## 1. วิสัยทัศน์

ระบบบริการจัดการร้านสักครบวงจร (Pieces Places Studio)  
ครอบคลุมหลายประเภทงานในร้านเดียวกัน และคิดแบ่งรายได้ถูกต้องตามกฎร้าน

ประเภทงานที่ระบุแล้ว:

- สัก
- ทำเล็บ
- ต่อขนตา
- คลาส
- อื่นๆ (เปิดกว้าง)

เป้าหมายหลักของระบบ = **ลงงาน → รับเงิน → อนุมัติ → จ่ายผู้ให้บริการ → ดูภาพรวมร้าน + ค่าใช้จ่าย**  
ไม่ใช่แค่จองคิว

## 2. บุคคล / Role (ระดับแนวคิด — ยัง custom ได้)

| บทบาท | ความหมายโดยประมาณ |
|---|---|
| ผู้ให้บริการ (Service Artist) | ช่างสัก / ทำเล็บ / ต่อขนตา / สอนคลาส — คนเดียวทำได้หลายประเภท |
| เจ้าของงาน | ผู้ให้บริการที่เป็นเจ้าของรายการงาน → ได้ส่วนแบ่ง Artist |
| ผู้เกี่ยวข้อง (collaborator) | ถูกเชิญให้ **ดู/แก้ไข** งานนั้นได้ — **ไม่ได้ส่วนแบ่ง** (ยกเว้นถ้าเป็น Referral คนละบทบาท) |
| ผู้แนะนำ (Referral) | ผู้ให้บริการ**ในระบบ** ที่ได้ % referral ของงานนั้น → เห็นงานนี้ในรายการของตัวเองเหมือนงานหนึ่งงาน ได้เฉพาะ % ของตัวเอง เข้าคิวจ่ายตามรอบเหมือนรายการอื่น |
| พนักงานหน้าเคาน์เตอร์ | มักสร้างงาน/รับเงินแทน; เห็นทุกรายการของทุกคน; อาจเป็นผู้อนุมัติด้วย |
| ผู้อนุมัติ | ตรวจการเงิน / ปิดงาน / อนุมัติเบิกล่วงหน้า / ยืนยันค่าใช้จ่าย |
| ผู้จ่ายเงิน | ยืนยันยอดจ่ายก้อน + แนบหลักฐานโอน (อาจเป็นคนเดียวกับผู้อนุมัติ) |
| Admin / เจ้าของร้าน | ตั้งค่า default split ตามหมวด; dashboard; แก้งานที่ปิดแล้วได้ |

หมายเหตุ: ระบบ role ต้อง **custom ได้ระดับหนึ่ง** — ยังไม่ออกแบบรายละเอียด permission matrix

แยกบทบาทบนงานหนึ่งใบให้ชัด:

- **เจ้าของงาน** = ได้ Artist %
- **Referral** = ได้ Referral % (และเห็นในลิสต์ของตัวเอง)
- **ผู้เกี่ยวข้อง** = สิทธิ์ดู/แก้เท่านั้น ไม่ได้เงิน
- คนสร้างงาน (เช่น เคาน์เตอร์) มักถูกใส่เป็นผู้เกี่ยวข้องอัตโนมัติ

## 3. Revenue Split

### 3.1 ค่า default ตามหมวด (admin ตั้งได้)

มีตาราง default ตามหมวด/เคส — admin ปรับได้  
ตอนสร้างงานระบบใส่ค่า default ให้เพื่อความสะดวกและให้รู้ว่าจะหักเท่าใด  
**ผู้ให้บริการแก้ % ต่องานได้** สำหรับเคสพิเศษ (ยืดหยุ่น)

ตัวอย่างโครงในหัว (ตัวเลขยังเป็นตัวอย่าง ไม่ล็อกเป็นของจริง):

| เคส | Artist | Referral | ร้าน |
|---|---|---|---|
| ช่างสักประจำ | 60% | 0% | 40% |
| ช่างสักประจำ + Referral | 60% | 5% | 35% |
| Guest — งานออกแบบของ Guest | 70% | 0% | 30% |
| Guest — ลูกค้ารีเควส Guest | 70% | 0% | 30% |
| Guest — งานล้น / งานทั่วไป | 50% | 0% | 50% |
| ทำเล็บ / ต่อขนตา | 70% | 0% | 30% |
| คลาส | 60% | 0% | 40% |
| คลาส + Referral | 60% | 10% | 30% |
| มัดจำถูกริบ (default) | 50% | 0% | 50% |

### 3.2 กฎที่ล็อกแล้ว

1. Default ตามหมวด + override ได้ต่องาน
2. มี Referral → คนแนะนำต้องเป็นผู้ให้บริการในระบบ; งานโผล่ในลิสต์ของเขา; ได้แค่ Referral %; เข้าคิวจ่ายตามรอบเหมือนงานอื่น
3. ผู้เกี่ยวข้อง ≠ ผู้ได้ส่วนแบ่ง
4. มัดจำยึด: default 50/50 ร้าน–เจ้าของงาน แต่ **แก้ได้ตอนกดสถานะยึดมัดจำ**
5. มัดจำคืน: กรอกจำนวนที่คืนลูกค้าได้ (ยืดหยุ่นตามข้อตกลง) — ส่วนที่เหลือในระบบยังต้องเคลียร์ว่าคิด split ยังไง
6. จ่ายส่วนแบ่ง (artist / referral / ยึดมัดจำ) ตามรอบของงานนั้นๆ เหมือนกัน

### 3.3 ฐานคิดยอด (ทิศทาง)

- มีฟิลด์ **ยอดเต็มงาน** ได้ตอนสร้าง แต่ **ไม่บังคับให้ตรงตอนจบ** เพราะราคาเปลี่ยนได้ตามหน้างาน (เพิ่มลาย / แก้ตามจริง)
- ยอดที่ใช้คิดเงินจริงน่าจะมาจาก **รายการรับเงินที่ approve** และเคสพิเศษ (ยึด/คืนมัดจำ) มากกว่าการล็อกยอดเต็มตอนสร้าง
- ยังไม่ล็อกสูตรคณิตศาสตร์แบบบรรทัดเดียว (เช่น net = sum(approved in) − refund)

## 4. Flow หลัก: งาน (Job / Work Order)

### 4.1 สร้างรายการงาน

ใครสร้างได้:

- ผู้ให้บริการเจ้าของงาน
- คนอื่นสร้างแทนได้ (เช่น เคาน์เตอร์) → คนสร้างอยู่ใน **ผู้เกี่ยวข้อง** และเห็นงานร่วมกับเจ้าของ
- เคาน์เตอร์เห็น **ทุกรายการของทุกคน**

ข้อมูลที่ใส่ตอนสร้าง (ที่ระบุแล้ว):

- ประเภทงาน / หมวด (ดึง default split)
- ชื่องาน
- เจ้าของงาน
- วันที่ (อาจมีหลายวันที่ — ยังไม่ชัด)
- รายละเอียดสไตล์งาน
- อัตราแบ่ง (default จากหมวด, แก้ได้)
- ผู้แนะนำ (referral) — optional, ต้องเป็น user ในระบบ
- ยอดเต็มงาน — optional / ประมาณการ เปลี่ยนทีหลังได้
- ผู้เกี่ยวข้องเพิ่มเติม (เชิญ user มาดู/แก้)

### 4.2 เพิ่มรายการรับเงิน (Payment entries)

- 1 งานมีได้หลายรายการ (มัดจำ, ส่วนที่เหลือ, เพิ่มระหว่างทาง, …)
- ใครเพิ่มได้: เจ้าของงาน หรือผู้เกี่ยวข้อง
- ข้อมูล: ช่องทางชำระ, จำนวนเงิน, แนบหลักฐาน, วันเวลาที่รับเงิน
- หลังบันทึก → **รอตรวจสอบจากผู้อนุมัติ**
- อนุมัติแล้วเข้าคำนวณ; **reject → ไม่นำมาคำนวณ** เก็บไว้พร้อม **เหตุผล reject**

### 4.3 เสร็จสิ้นงาน (ปิดฝั่งผู้ให้บริการ)

เงื่อนไขโดยประมาณ:

- ให้บริการเสร็จและรับเงินตามที่ใช้จริง  
  **หรือ** ลูกค้าไม่มา → **ยึดมัดจำ** (แก้ % ได้ตอนกด) / **คืนมัดจำ** (กรอกยอดคืน)

กดเสร็จสิ้นแล้ว → สถานะงาน **รออนุมัติ (ปิดงาน)**

### 4.4 ผู้อนุมัติยืนยันปิดงาน

- ตรวจการเงิน/ข้อมูล แล้วกดยืนยันปิดงาน
- งานเข้าสู่ **คิวรอจ่าย** (รอบปกติหรือเบิกล่วงหน้า)
- หลังอนุมัติปิด: เจ้าของงาน/ผู้เกี่ยวข้อง **แก้ไม่ได้**  
  แก้ได้เฉพาะผู้อนุมัติ / admin
- สร้าง entitlement ให้เจ้าของงาน (Artist %) และ Referral (ถ้ามี) — คนแนะนำเห็นเป็นรายการในลิสต์ของตัวเอง

### 4.5 รอบจ่ายเงิน (Payout cycle)

- ทุกวันที่ **1** และ **16** ของทุกเดือน
- รวมยอดค้างจ่ายต่อผู้ให้บริการจากงาน/ส่วนแบ่งที่อนุมัติแล้วและยังไม่จ่าย → **โอนก้อนเดียวต่อคน**
- ผู้จ่ายเงินยืนยันยอดก้อนต่อคน + แนบหลักฐานโอน
- สถานะ: **อนุมัติรอจ่ายเงิน** → จ่ายแล้ว

### 4.6 เบิกเงินล่วงหน้า (Advance)

- เลือกได้ **หลายงาน** ที่อนุมัติปิดแล้ว
- รวมยอดแบบเดียวกับรอบจ่ายปกติ แล้วจ่ายก่อนรอบ 1/16
- งานที่ถูกเบิกแล้วไม่ควรโผล่ซ้ำในรอบปกติ

## 5. ค่าใช้จ่ายร้าน (Expenses)

หมวดตัวอย่าง: แอลกอฮอล์, ค่าเรียนช่าง, ถุงมือ S10/M10, ทิชชู่, ค่าน้ำไฟ/ค่าเช่า

กฎ:

- แต่ละคนใส่แทนกันได้
- ผู้อนุมัติยืนยันทุกรายการ
- reject (ทิศทางเดียวกับ payment): น่าจะไม่นำมาคำนวณ + ใส่เหตุผล — ยังไม่ยืนยันแยกจาก payment แต่สอดคล้องกับข้อ 7

## 6. Dashboard (Admin / เจ้าของร้าน)

ต้องการดูได้หลากหลายผ่าน **filter ครอบคลุม** เช่น:

- ยอดผู้ให้บริการแต่ละคน
- หมวดค่าใช้จ่าย
- รายรับ / รายจ่าย / กำไร
- อื่นๆ ตามมิติที่ตั้งได้ (ช่วงเวลา, ประเภทงาน, …)

ยังไม่ล็อกสูตรกำไรแบบทางการ — ทิศทาง: ส่วนร้านจากงานที่ปิดแล้ว − expense ที่ approve (รอ confirm)

## 7. สถานะโดยประมาณ (State machine — draft)

### งาน (Job)

```
open
  → awaiting_job_approval   (กดเสร็จสิ้น / ยึดมัดจำ / คืนมัดจำ)
  → approved_pending_payout
  → in_payout_or_advance / paid
```

เคสจบพิเศษ: `forfeit_deposit` | `refund_deposit` (มากับการกดเสร็จสิ้น)

### รายการรับเงิน (Payment entry)

```
pending_review → approved | rejected (เก็บเหตุผล, ไม่นำมาคำนวณ)
```

### ส่วนแบ่งต่อคนบนงาน (Payout entitlement)

```
pending_job_approval → eligible → included_in_batch → paid
```

(เจ้าของงานและ Referral คนละ entitlement บนงานเดียวกัน)

### รอบจ่าย / เบิกล่วงหน้า (batch ต่อคน)

```
draft_selection → approved_awaiting_transfer → paid
```

### ค่าใช้จ่าย (Expense)

```
pending_approval → approved | rejected (เหตุผล; ไม่นับในรายงาน — สมมติ)
```

## 8. Decisions ที่ล็อกแล้ว (จากคำตอบล่าสุด)

| # | หัวข้อ | คำตอบ |
|---|---|---|
| 1 | ฐานคิด % / default | default ตามหมวด ตั้งโดย admin; แก้ต่องานได้ |
| 2 | ยอดเต็มงาน | มีได้ตอนสร้าง แต่ราคาจบงานเปลี่ยนได้ตามหน้างาน |
| 3 | Referral | user ในระบบ; เห็นงานในลิสต์ตัวเอง; ได้ % ตัวเอง; จ่ายตามรอบ |
| 4 | มัดจำยึด/คืน | ยึด default 50/50 แก้ตอนกดได้; คืนกรอกยอดคืนได้; จ่ายตามรอบ |
| 5 | ผู้เกี่ยวข้อง | ดู/แก้เท่านั้น ไม่ได้ส่วนแบ่ง (คนละเรื่องกับ Referral) |
| 6 | เบิกล่วงหน้า | เลือกได้หลายงานที่อนุมัติแล้ว รวมยอดแบบรอบจ่าย |
| 7 | Reject | ไม่นำมาคำนวณ + ใส่เหตุผล (ยัง “ทิ้งไว้” ตามที่คิดได้ตอนนี้) |
| 8 | Dashboard | filter หลากหลาย (ต่อช่าง, หมวด expense, ฯลฯ) |

### Assumptions ที่ยังสมมติ (รอ confirm เบาๆ)

1. งานหนึ่งมีเจ้าของงาน Artist คนเดียว (ช่วยสักสองคนยังไม่เล่า)
2. เคาน์เตอร์ / ผู้อนุมัติ / ผู้จ่ายเงิน role ทับกันได้
3. Google login สำหรับคนในร้าน — ลูกค้ายังไม่เข้าสู่ระบบ
4. ยอดคิด split หลัก = เงินเข้าที่ approve หักยอดคืนลูกค้า (ถ้ามี)
5. Reject ของ expense ใช้กฎเดียวกับ payment

## 10. ช่องว่างที่ยังเหลือ

### เงิน / คำนวณ (เหลือละเอียด)

1. สูตรยอดที่ใช้คูณ % ชัดๆ: `sum(payment approved) − refund_amount` ใช่ไหม? มัดจำยึดใช้แค่ยอดมัดจำที่ยึด?
2. ถ้ารับเงินเกิน/ต่ำกว่า “ยอดเต็ม” ตอนปิดงาน ระบบบล็อกหรือแค่เตือน?
3. มี Referral แล้วเปลี่ยนคนแนะนำหลังมี payment ได้ไหม?
4. Guest vs ประจำ: เลือกจากโปรไฟล์คน หรือเลือกเคสตอนสร้างงาน?

### มัดจำคืน (ยังบาง)

1. คืนจากเงินที่รับมาแล้ว → ส่วนที่เหลือหลังคืน ยังแบ่ง artist/ร้านตาม % ปกติไหม?
2. คืนเต็มมัดจำ = เจ้าของงานได้ 0 ใช่ไหม?
3. บันทึกการคืนเป็น payment ฝั่งออก หรือฟิลด์บนงาน?

### Lifecycle / สิทธิ์

1. ผู้เกี่ยวข้องแก้ได้ทุกอย่างที่เจ้าของแก้ได้ไหม จนถึงก่อนปิดงาน?
2. กดเสร็จสิ้นได้ใครบ้าง? (เจ้าของเท่านั้น / ผู้เกี่ยวข้องด้วย)
3. สถานะระหว่างทางก่อนเสร็จ (นัดแล้ว / กำลังทำ) ต้องมีไหม หรือ open จนกดเสร็จก็พอ?
4. ยกเลิกงานทั้งใบ — ใครทำได้ ตอนไหน?
5. งานที่ payment ถูก reject หมด ยังกดเสร็จสิ้นได้ไหม?

### รอบจ่าย

1. ตัดรอบ timezone / เวลาสิ้นสุดรอบ?
2. งาน approve หลังตัดรอบ → รอบถัดไปอัตโนมัติ ใช่ไหม?
3. เบิกหลายงาน = จ่ายเต็ม entitlement ของงานเหล่านั้นเสมอ หรือลดยอดเองได้?
4. จ่ายผิด/แก้หลักฐานโอนหลัง paid ทำยังไง?
5. ในลิสต์ของคน Referral แสดงเป็นงานเดียวกัน (read-only ส่วนใหญ่) หรือเป็น “รายการ entitlement” แยก?

### Expense / Dashboard

1. หมวด expense เป็น master ที่ admin เพิ่มเองได้ไหม?
2. สูตรกำไรบน dashboard ล็อกเป็นอะไร?
3. ตัวเลข “ยอดผู้ให้บริการ” = ที่จ่ายแล้ว / ค้างจ่าย / ทั้งคู่?

### ลูกค้า / งานบริการ / Auth
