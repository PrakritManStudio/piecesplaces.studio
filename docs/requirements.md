# piecesplaces.studio — Requirements (draft)

สถานะ: ล็อกกฎเงินหลักแล้ว — เงินเก็บเป็น integer satang (1 THB = 100); floor rounding เหลือให้ร้าน  
อัปเดตล่าสุด: 2026-09-23 (satang + Guest A/B + ริบ 50/50 ไม่มี refer + รอบ 1/16 Asia/Bangkok)

---

## 1. วิสัยทัศน์

ระบบบริการจัดการร้านสักครบวงจร (Pieces Places Studio)  
ครอบคลุมหลายประเภทงานในร้านเดียวกัน และคิดแบ่งรายได้ถูกต้องตามกฎร้าน

ประเภทงานที่ระบุแล้ว:

- สัก
- ทำเล็บ
- ต่อขนตา
- คลาส
- อื่นๆ (เปิดกว้าง)

เป้าหมายหลักของระบบ = **ลงงาน → รับเงิน → อนุมัติ → จ่ายผู้ให้บริการ → ดูภาพรวมร้าน + ค่าใช้จ่าย**  
ไม่ใช่แค่จองคิว

## 2. บุคคล / Role (ระดับแนวคิด — ยัง custom ได้)

| บทบาท | ความหมายโดยประมาณ |
|---|---|
| ผู้ให้บริการในระบบ (ประจำ ฯลฯ) | มีบัญชี login; ช่างสัก / ทำเล็บ / ต่อขนตา / สอนคลาส — คนเดียวทำได้หลายประเภท |
| ช่าง Guest | **ไม่มี login**; admin สร้างโปรไฟล์ (ชื่อ + ข้อมูลน้อยๆ); ร้านลงงานให้; เงินเคลียร์**วันจบงาน** ไม่เข้าคิว 1/16 |
| เจ้าของงาน | ผู้ให้บริการที่เป็นเจ้าของรายการ → ได้ส่วนแบ่ง Artist (ถ้าเป็น Guest จะจ่าย/หักคนละแบบ — ดู §3.5) |
| ผู้เกี่ยวข้อง (collaborator) | user ในระบบที่ถูกเชิญให้ **ดู/แก้ไขได้เท่าเจ้าของงาน** จนถึงก่อนปิดงาน (รวมกดเสร็จสิ้น) — **ไม่ได้ส่วนแบ่ง** |
| ผู้แนะนำ (Referral) | ผู้ให้บริการ**ในระบบ** ได้ Referral %; เห็นงานในลิสต์ตัวเอง; จ่ายตามรอบ 1/16 หรือเบิก |
| พนักงานหน้าเคาน์เตอร์ | สร้างงาน/รับเงินแทน; เห็นทุกงาน; มักลงงาน Guest ให้; อาจเป็นผู้อนุมัติ |
| ผู้อนุมัติ | ตรวจการเงิน / ปิดงาน / settlement Guest / เบิกล่วงหน้า / ยืนยันค่าใช้จ่าย |
| ผู้จ่ายเงิน | ยืนยันยอดจ่ายก้อน + หลักฐานโอน (รอบ 1/16 / เบิก) — Guest เคลียร์วันงานอาจคนละพิธี |
| Admin / เจ้าของร้าน | ตั้ง default split; dashboard; แก้งานที่ปิดแล้วได้ |

หมายเหตุ: role **custom ได้ระดับหนึ่ง** — ยังไม่ออกแบบ permission matrix

แยกบทบาทบนงานหนึ่งใบ:

- **เจ้าของงาน** = ได้ Artist % (หรือในเคส Guest = ฝั่งเงินตาม §3.5)
- **Referral** = ได้ Referral % (ต้องมีบัญชี)
- **ผู้เกี่ยวข้อง** = สิทธิ์ดู/แก้/เสร็จสิ้น เช่นเดียวกับเจ้าของ — ไม่ได้เงิน
- คนสร้างงาน (เช่น เคาน์เตอร์) มักถูกใส่เป็นผู้เกี่ยวข้องอัตโนมัติ

## 3. Revenue Split

### 3.1 ค่า default ตามหมวด (admin ตั้งได้)

มีตาราง default ตามหมวด/เคส — admin ปรับได้  
ตอนสร้างงานใส่ default ให้; **แก้ % ต่องานได้** สำหรับเคสพิเศษ

ตัวอย่างโครงในหัว (ตัวเลขยังไม่ล็อก):

| เคส | Artist | Referral | ร้าน |
|---|---|---|---|
| ช่างสักประจำ | 60% | 0% | 40% |
| ช่างสักประจำ + Referral | 60% | 5% | 35% |
| Guest — หาลูกค้าเอง (เคส A: ออกแบบ / รีเควส) | 70% | 0% | 30% |
| Guest — ร้านส่งงาน (เคส B: งานล้น / ทั่วไป) | 50% | 0% | 50% |
| ทำเล็บ / ต่อขนตา | 70% | 0% | 30% |
| คลาส | 60% | 0% | 40% |
| คลาส + Referral | 60% | 10% | 30% |
| มัดจำถูกริบ (default) | 50% | 0% | 50% |

### 3.2 กฎที่ล็อกแล้ว (ทั่วไป)

1. Default ตามหมวด + override ได้ต่องาน
2. Referral = user ในระบบ; เห็นงานในลิสต์; ได้แค่ %; จ่ายตามรอบ/เบิก
3. ผู้เกี่ยวข้อง ≠ ผู้ได้ส่วนแบ่ง แต่สิทธิ์แก้/เสร็จสิ้นเท่าเจ้าของงาน (ก่อนปิด)
4. มัดจำจบได้แค่ 2 ทาง: **ริบเต็ม** หรือ **คืนเต็ม** — ไม่มีคืนบางส่วน
5. **ริบมัดจำมีเคสเดียวเสมอ**: 50% ร้าน / 50% เจ้าของงาน — **ไม่มี Referral** (แม้งานนั้นมี refer ก็ไม่จ่ายฝั่ง refer ตอนริบ)
6. คืนมัดจำ = คืนลูกค้าเต็มจำนวน (Guest: คืนได้ทันที)
7. Guest % งานปกติ: **หาลูกค้าเอง = Artist 70 / ร้าน 30**; **ร้านส่งงาน = Artist 50 / ร้าน 50** (map ตรงกับทิศทางเงิน A/B)
8. เบิกล่วงหน้า: จ่ายตามจำนวนที่จะได้ของงานที่เลือก **เต็ม entitlement** ไม่ลดเอง
9. Reject payment/expense: ไม่นำมาคำนวณ + เหตุผล

### 3.3 ฐานคิดยอด (ทิศทาง — ช่างประจำ / คนมีบัญชี)

- ยอดเต็มงานมีได้ตอนสร้าง แต่ราคาจบเปลี่ยนตามหน้างานได้
- ยอดคิดจริงน่าจะจากรายการรับเงินที่ approve
- มัดจำ: ริบ → **50% ร้าน / 50% เจ้าของงาน เท่านั้น ไม่มี refer**; คืนเต็ม → คืนลูกค้า (Guest คืนได้ทันที)
- Guest งานปกติ: เคส A (ลูกค้าของ Guest) 70/30; เคส B (ร้านส่ง) 50/50 — สอดคล้องทิศทางเงิน

### 3.4 โปรไฟล์ Guest

- **ไม่มี login**
- **Admin เป็นคนเพิ่ม** บัญชี/โปรไฟล์ประเภท Guest
- ข้อมูลเก็บน้อย: **ชื่อเป็นหลัก** + ฟิลด์เสริมเท่าที่มี (ไม่บังคับครบ)
- ใช้ผูกเป็น “เจ้าของงาน” บนจ็อบ Guest โดยร้าน/เคาน์เตอร์เป็นคนลงให้

### 3.5 เงิน Guest (คนละ pipeline กับรอบ 1/16)

เคลียร์เงิน **ณ วันจบงานที่ร้าน** ไม่รอรอบ 1 กับ 16  
รายการบันทึกเงิน settlement (รับส่วนร้านจาก Guest / จ่ายให้ Guest ฯลฯ): **ใครก็เพิ่มได้** แต่ต้อง **รออนุมัติจากผู้อนุมัติชุดเดียวกับที่อนุมัติรายการอื่น**

#### เคส A — Guest หาลูกค้ามาเอง ใช้ร้านเป็นสถานที่  
อัตราปกติ: **Artist 70% / ร้าน 30%** · เงินลูกค้าเข้าบัญชี Guest ก่อน → วันจบงาน Guest จ่ายส่วนร้าน

1. ช่าง Guest รับเงินจากลูกค้าเข้าบัญชีส่วนตัว
2. จบงานแล้ว Guest จ่ายส่วนร้านวันนั้น
3. บันทึกในระบบ → รออนุมัติ

#### เคส B — คิวช่างประจำเต็ม ร้านส่งงานให้ Guest  
อัตราปกติ: **Artist 50% / ร้าน 50%** · เงินลูกค้าเข้าร้านก่อน → วันจบงานร้านจ่าย Guest

1. เงินลูกค้าเข้าร้านก่อน
2. ร้านหักแล้วจ่าย Guest วันนั้น
3. บันทึก → รออนุมัติ

| | % Artist / ร้าน (งานปกติ) | เงินลูกค้าเข้าที่ | เคลียร์วันจบงาน | คิว 1/16 Artist? |
|---|---|---|---|---|
| ช่างประจำ | ตามหมวด (เช่น 60/40) | ร้าน | รอบ 1/16 หรือเบิก | ใช่ |
| Guest เคส A | **70 / 30** | บัญชี Guest | Guest จ่ายส่วนร้าน | ไม่ |
| Guest เคส B | **50 / 50** | ร้าน | ร้านจ่าย Guest | ไม่ |

ริบมัดจำ (ทุกประเภท รวม Guest A/B และประจำ): **50% ร้าน / 50% เจ้าของงาน — ไม่มี Referral**

Referral บนงาน Guest ตอนจบปกติ (ไม่ใช่ริบ) — **ไม่มี** (งาน Guest ห้าม referral)

## 4. Flow หลัก: งาน (Job / Work Order)

### 4.1 สร้างรายการงาน

- เจ้าของงานสร้างเองได้ (ถ้ามีบัญชี)
- คนอื่นสร้างแทนได้ → อยู่ในผู้เกี่ยวข้อง
- เคาน์เตอร์เห็นทุกงาน; **งาน Guest สร้างโดยร้าน/เคาน์เตอร์** (Guest ไม่ login)
- เจ้าของงาน Guest = เลือกจากโปรไฟล์ที่ admin สร้างไว้
- ต้องระบุ/เลือกได้ว่าเป็น Guest เคส A หรือ B (หรือหมวดที่ mirror สองเคสนี้) เพราะทิศทางเงินคนละแบบ

ข้อมูลตอนสร้าง (ที่ระบุแล้ว):

- ประเภทงาน / หมวด (ดึง default split)
- ชื่องาน
- เจ้าของงาน (user ในระบบ หรือโปรไฟล์ Guest ที่ admin เพิ่ม)
- วันที่
- รายละเอียดสไตล์
- อัตราแบ่ง (default + แก้ได้)
- ผู้แนะนำ (optional, ต้องเป็น user)
- ยอดเต็มงาน (optional / ประมาณการ)
- ผู้เกี่ยวข้อง

### 4.2 รายการรับเงิน

- หลายรายการต่องาน; รออนุมัติ; reject ไม่คำนวณ + เหตุผล
- เคส Guest A: เงินจริงอยู่ในมือ Guest — รายการในระบบอาจเป็น “บันทึกว่าได้รับแล้วที่ Guest” + รายการ “ร้านได้รับส่วนหัก” คนละชนิด  
  (รายละเอียดชนิด payment ยังไม่ออกแบบ)
- เคส Guest B: เงินเข้าร้านตามปกติ แล้วมีรายการจ่ายออกให้ Guest วันจบงาน
- รายการเหล่านี้ **ใครก็เพิ่มได้** แต่สถานะรออนุมัติจากผู้อนุมัติชุดเดียวกับ payment/ปิดงาน

### 4.3 เสร็จสิ้นงาน

- กดได้โดย **เจ้าของงานหรือผู้เกี่ยวข้อง** (งาน Guest: ผู้เกี่ยวข้อง/เคาน์เตอร์ เพราะ Guest ไม่ login)
- จบบริการปกติ หรือ มัดจำ: **ริบเต็ม** / **คืนเต็ม** เท่านั้น
- หลังกด → รออนุมัติปิดงาน
- Guest: มีรายการ settlement วันงาน (รับส่วนร้าน หรือ จ่าย Guest) → อนุมัติแยก/คู่กับการปิด — ไม่โยนเข้าคิว 1/16 ฝั่ง Artist

### 4.4 ผู้อนุมัติปิดงาน / อนุมัติรายการเงิน

- ชุดผู้อนุมัติเดียวกันสำหรับ: payment, ปิดงาน, settlement Guest, expense, เบิก
- หลังปิด: เจ้าของ/ผู้เกี่ยวข้องแก้ไม่ได้ — เหลือผู้อนุมัติ/admin
- ช่างประจำ (+ Referral): สร้าง entitlement เข้าคิวจ่าย
- Guest Artist: ไม่สร้าง entitlement รอบ 1/16 — ใช้ settlement วันงานที่อนุมัติแล้ว

### 4.5 รอบจ่าย 1 และ 16

- รวมยอดค้างของผู้ให้บริการ**ที่มีบัญชี** จากงานที่อนุมัติแล้วและยังไม่จ่าย/ยังไม่เบิก
- โอนก้อนเดียวต่อคน + หลักฐาน

### 4.6 เบิกล่วงหน้า

- เลือกได้หลายงานที่อนุมัติแล้ว
- จ่าย **ตามจำนวนที่จะได้ของงานที่เลือก** (เต็ม) รวมยอดแบบรอบจ่าย
- งานที่เบิกแล้วไม่โผล่ซ้ำในรอบปกติ
- ใช้กับคนมีบัญชี (ไม่ใช่ pipeline Guest วันงาน)

## 5. ค่าใช้จ่ายร้าน (Expenses)

หมวดตัวอย่าง: แอลกอฮอล์, ค่าเรียนช่าง, ถุงมือ, ทิชชู่, ค่าน้ำไฟ/ค่าเช่า  
ใส่แทนกันได้; อนุมัติทุกรายการ; reject ไม่นับ + เหตุผล (สมมติ)

## 6. Dashboard

Filter หลากหลาย: ยอดผู้ให้บริการ, หมวด expense, รายรับ/รายจ่าย/กำไร, ช่วงเวลา, ประเภทงาน, …  
ควรแยกหรือ filter ได้ว่าเป็นเงินจาก Guest เคส A/B กับช่างประจำ — ยังไม่ล็อก UI

## 7. สถานะโดยประมาณ (draft)

### งาน

```
open
  → awaiting_close_approval   (เสร็จสิ้น | ริบมัดจำเต็ม | คืนมัดจำเต็ม)
  → closed
       ├─ (ประจำ) PayoutEntitlement → รอบ 1/16 หรือ advance → paid
       └─ (Guest) same-day PaymentEntry (shop_cut / payout_to_guest / refund) → อนุมัติ
```

### Payment entry

```
pending → approved | rejected (+ reason, ไม่คำนวณ)
```

ชนิด: `inbound_shop` | `inbound_held_by_guest` | `shop_cut_from_guest` | `payout_to_guest` | `refund_to_customer`

### Entitlement (เฉพาะผู้มีบัญชี / งาน guestEngagement=none)

```
payoutBatchId null → in batch (cycle|advance) → batch paid
```

### เงิน

integer satang ทุกที่ (1 THB = 100); floor rounding; เศษเหลือให้ร้าน

## 8. Decisions ที่ล็อกแล้ว

| หัวข้อ | คำตอบ |
|---|---|
| Default split | ตามหมวด admin ตั้ง; แก้ต่องานได้ |
| ยอดเต็มงาน | มีได้; ราคาจบเปลี่ยนตามหน้างานได้ |
| Referral | user ในระบบ; ลิสต์ของตัวเอง; % ตัวเอง; รอบ/เบิก |
| มัดจำ | ริบเต็ม หรือ คืนเต็ม เท่านั้น |
| ริบมัดจำ | **เคสเดียว: 50% ร้าน / 50% เจ้าของงาน — ไม่มี refer** (ใช้ทั้งประจำและ Guest) |
| คืนมัดจำ | เต็มจำนวน; Guest คืนได้ทันที |
| Guest % + ทิศทางเงิน | หาลูกค้าเอง = 70/30 + เงินเข้า Guest; ร้านส่ง = 50/50 + เงินเข้าร้าน; เคลียร์วันจบงาน |
| ผู้เกี่ยวข้อง | ดู/แก้/เสร็จสิ้นเท่าเจ้าของ (ก่อนปิด); ไม่ได้ส่วนแบ่ง |
| เบิกล่วงหน้า | หลายงาน; จ่ายเต็มจำนวนที่จะได้ของงานที่เลือก |
| Reject | ไม่คำนวณ + เหตุผล |
| Dashboard | filter หลากหลาย |
| Guest โปรไฟล์ | admin เพิ่ม; ชื่อ + ข้อมูลน้อยๆ; ไม่มี login |
| Guest เงิน | เคลียร์วันจบงาน; เคส A/B คนละทิศทาง; ใครก็บันทึกได้แต่ต้องอนุมัติ (ผู้อนุมัติชุดเดียว) |

### Assumptions ที่ยังสมมติ

1. งานหนึ่งมีเจ้าของ Artist คนเดียว
2. เคาน์เตอร์ / ผู้อนุมัติ / ผู้จ่ายเงิน ทับ role ได้
3. Login (Google) สำหรับคนในร้านเท่านั้น — Guest และลูกค้าไม่มีบัญชี
4. “ใครก็เพิ่มได้” ของข้อ settlement = user ที่ login แล้วทุกคน (หรือทุก role ที่มีสิทธิ์ลงงาน) — ยังไม่แย่ว่าจำกัด role
5. Referral บนงาน Guest ยังจ่ายตามรอบให้คนแนะนำ
6. Reject expense = กฎเดียวกับ payment

## 10. ช่องว่างที่ยังเหลือ

### Guest (เหลือ)

1. งาน Guest ต้องอนุมัติปิดก่อน/คู่กับ settlement ไหม หรือ settlement อย่างเดียวพอ?
2. ~~มัดจำ / % map A·B~~ → ล็อกแล้ว (70/30, 50/50; ริบ 50/50 ไม่มี refer)
3. Referral บนงาน Guest ตอนจบ**ปกติ** (ไม่ใช่ริบ) มีได้ไหม?
4. ฟิลด์เสริมบนโปรไฟล์ Guest (เบอร์ / โน้ต / ว่างไว้ก่อน)?
5. ตอนริบ ฝั่งเจ้าของงานที่เป็น Guest ได้ 50% วันนั้นเลยไหม (ตาม pipeline A/B) หรือเข้าอย่างอื่น?

### เงินช่างประจำ (ละเอียด)

1. สูตรยอดคูณ % = `sum(approved in)` เมื่อริบใช้ยอดมัดจำ; เมื่อคืนเต็มมัดจำ = ไม่มี entitlement จากมัดจำ — ใช่ไหม?
2. รับเกิน/ต่ำยอดเต็มตอนปิด — บล็อกหรือเตือน?
3. เปลี่ยน Referral หลังมี payment ได้ไหม?

### Lifecycle

1. สถานะระหว่างทาง (นัดแล้ว / กำลังทำ) ต้องมีไหม?
2. ยกเลิกงานทั้งใบ — ใคร ตอนไหน?
3. payment reject หมดแล้วยังเสร็จสิ้นได้ไหม?

### รอบจ่าย

1. timezone / เวลาตัดรอบ
2. approve หลังตัดรอบ → รอบถัดไปอัตโนมัติ?
3. จ่ายผิด/แก้หลักฐานหลัง paid
4. ลิสต์ Referral แสดงงานใบเดียวหรือ entitlement แยก?

### อื่นๆ

1. หมวด expense master admin เพิ่มเองได้?
2. สูตรกำไร dashboard
3. โปรไฟล์ลูกค้า vs ข้อความบนงาน
4. ไฟล์แนบสไตล์
5. คลาส = ครั้ง / คอร์ส / นักเรียน
6. เก็บเลขบัญชีผู้ให้บริการในโปรไฟล์?
